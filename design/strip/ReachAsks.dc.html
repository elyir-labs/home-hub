B — the strip asks, and the hub answers if it was expecting it

It looks us up, the way it already looks the broker up.

Once commissioned the strip is on the house network. It asks mDNS whether a hub of ours is there, and if one answers it asks for a token — and the hub gives one only to a device it commissioned in the last few minutes. No new cluster, no Vendor ID, nothing that waits on certification.

For

Buildable today, on a test vendor id, with nothing waiting on anybody. It is also the only direction that works for a strip somebody else commissioned and later shared to us, because it does not depend on our having been the fabric that set it up. And the hub already answers mDNS and already hands out tokens — pairing.py does it for phones — so the shape is one the house knows.

Against

It is a route that gives something away, on the LAN, to whoever asks first. The window is the only thing protecting it, and a window is a weaker promise than an encrypted session that already exists. Anything on the network during those minutes can try, and the hub cannot tell one caller from another except by timing.

The thing that would make it safe, and it is not free

The hub knows which device it just commissioned, so it could require the caller to prove it is that node — a nonce over the Matter session, then presented on the LAN. That closes the hole properly and turns this into direction A with extra steps. Which is the honest summary: B is A without the Vendor ID, and it is either a bit insecure or it is A.
